## 为什么要这份基线

检索的既有参数里，`MAX_DISTANCE=0.55` 是实测标定的（相关查询 l2 距离
0.3625~0.4722、无关查询 0.6402~0.6981 的分离带中点），但：

- **切片长度**从来没有对着 embedding 的真实窗口量过。`CHUNK_SIZE` 原来是 600 字，
  而 `BAAI/bge-small-zh-v1.5` 的 `sentence_bert_config.json` 写的是
  `max_seq_length: 512`（`config.json` 的 `max_position_embeddings` 同为 512）。
  中文下 1 字≈1 token，超出部分会被 tokenizer **静默截断**。
- 没有任何评测集，所以「改了检索之后是变好还是变坏」无法回答。

## 评测集

- 语料：`tests/fixtures/eval_corpus/`，6 个合成文件（财务指标 / 考勤假期 /
  客户分级 / 数据备份 / 费用报销 / 长段落压测），总计约 6 KB。
- 最后一个文件（`06-长段落与窗口压测.md`）刻意放了一段**只有逗号、没有任何句末标点**的
  超长文本：普通段落都比 `chunk_size` 短，不这样构造的话「硬切」分支永远不会被触发，
  切窗诊断就永远是 0，也就根本测不出「chunk 尺寸超出 embedding 窗口」这件事。
  它的正文写的是青花瓷烧制工艺——**主题必须和其余 30 条查询彻底无关**，
  原因见「踩到的坑」。
- 标注：`tests/fixtures/eval_queries.json`，30 条正样本 + 5 条负样本。
- **标注按「命中片段文本 + 预期文件」而不是 chunk id**：换切片后 chunk id 必然全变，
  按文本标注才能让改动前后可比。
- 负样本被一条测试约束为**与语料无任何词面重叠**（否则关键词兜底会召回它们，
  误召回率就不再反映阈值好坏）；gold_phrase 也被一条测试约束为**必须真的能在语料里找到**。

## 怎么跑

**注意：`config.CHUNK_SIZE` 已经改成 480，所以「改动前」必须显式 `--chunk-size 600`。**

```bash
# 改动前：显式 600
python scripts/eval_retrieval.py --chunk-size 600 --calibrate --verbose \
    --json docs/baseline-p0-before.json

# 改动后：用默认 480
python scripts/eval_retrieval.py --calibrate --verbose \
    --json docs/baseline-p0-after.json
```

默认模式**不调大模型**（query = 原问题）、**用内存向量库**（`EphemeralClient`，
不碰真实 `chroma_db/`）。要看真实 HyDE 路径（会花 API 额度）再加 `--hyde`。

## 结果（合成评测集，2026-10-06 定稿）

| 指标 | 改动前（`--chunk-size 600`） | 改动后（480，含块边界修复） |
| --- | --- | --- |
| 切片结果 | 6 个文件 / **5 个 chunk** | 6 个文件 / **8 个 chunk** |
| **超过 512 token 的 chunk** | **2/5**（521 / 528 token，中位 524） | **0/8** |
| recall@5 | **1.000（30/30）** | **1.000（30/30）** |
| MRR | 0.944 | **0.961** |
| 负样本误召回率 | 0.000（0/5） | 0.000（0/5） |
| 正样本命中块距离 | min 0.2384 / max 0.5898 | min 0.2479 / max 0.5900 |
| 负样本最小距离 | min 0.6168 / max 0.7100 | min 0.5875 / max 0.6917 |
| 建议 MAX_DISTANCE | 0.6033（当前 0.55） | 分不开（正负重叠） |
| 耗时 | 0.7s（35 条样本） | 0.7s（35 条样本） |

**三条结论：**

1. **P1-1 得到直接证据**：600 时有 2 个块（521、528 token）超出 512 窗口，尾部内容不参与
   向量；480 时 8 个块全部在窗口内。这正是「把 `CHUNK_SIZE` 调到 480」要解决的问题，
   而且是量出来的，不是推出来的。
2. **没有回退，反而略好**：recall@5 两次都是 1.000（30/30）；MRR 0.944 → **0.961**
   （q24 从 rank 2 升到 rank 1）；负样本误召回率两次都是 0.000。名次分布也很稳：
   q13 rank 2、q16 rank 3，两次一致。
3. **`MAX_DISTANCE` 保持 0.55 不动。** 两条理由互相印证：
   - 480 这一次的正负分离带**重叠**了（正样本 max 0.5900 > 负样本 min 0.5875），
     脚本直接报「分不开」；600 那次给出的 0.6033 也不可用——它只比负样本最小距离
     低一点点，换个语料就会翻车。
   - 这次标定是 `--no-hyde`（query 就是短问句本身）测的，而线上走 HyDE——生成的是
     「文档式」长文本，距离整体更小（历史标定：相关查询 0.3625~0.4722、无关查询
     0.6402~0.6981，中点是 0.55）。拿这条路径的分离带去放宽线上阈值，方向就是错的。
   - 值得记一笔：480 下有一条正样本（q16）的最佳距离是 **0.5900 > 0.55**，向量路径
     判为未命中，最终靠关键词兜底捞回到 rank 3。说明 0.55 在短问句模式下确实偏紧，
     但这属于「no-hyde 标定」，不能直接拿来改线上值。
   - 结论：**保持 0.55**；想真正重标，得用真实语料 + `--hyde` 重跑，而不是靠合成语料。
     真实语料的两种口径都已实测（见「真实语料」一节）：HyDE 口径下真实提问 0/12 超线、
     但正负两侧仍然重叠，所以**没有支持换值的证据**，0.55 继续保留。

## 踩到的坑（都会影响指标，记下来免得下次再犯）

1. **`06` 的主题选错了会污染整份评测**。第一版 `06` 写的是「切片/向量/检索」这类元话题，
   结果：q03（「ROE 可以怎么拆解」）从 rank 1 掉成**完全未命中**——因为它的长块在语义上
   比 ROE 那块更接近「拆解」；同时负样本最小距离从 0.6447 掉到 0.568，分离带直接消失。
   教训：**压测用的语料必须和全部查询话题正交**，否则它自己就成了干扰项。
   现已把 `06` 正文换成青花瓷工艺；换主题后 q03 回到 rank 1、recall@5 回到 1.000、
   负样本最小距离回到 0.5875 以上（上面的定稿数字就是换主题之后测的）。
2. **负样本撞词是真的会翻车**。`n04` 是「光合作用的光反应阶段」，它的 2-gram「作用」
   一旦出现在语料里，那条保险丝立刻变红。第一版 `06` 里顺手写的「承担两个作用」
   就是这么被抓出来的——保险丝按设计工作了。
3. **切窗诊断必须有超长段落才有效**。第一版语料每段都短于 `chunk_size`，硬切分支不触发，
   600 和 480 都会报 0 超窗；补了 `06` 才有 `2/6 → 0/9` 这个对照。

## P1 实际改了什么（含与原始计划的差异）

| 项 | 计划 | 实际 | 差异原因 |
| --- | --- | --- | --- |
| `CHUNK_SIZE` | 600 → 480 | 已改（`src/config.py`），并同步 `.env.example` / `README.md` / `AGENTS.md` / `CLAUDE.md` | 一致 |
| 切片本身 | 计划里没提 | **额外修了 `src/pdf_ingestion.py` 的一个真问题** | 见下 |
| context 装配 | 按块边界，不再硬切 | 已改（`src/llm.py`），且「按相关度选块、按原文序摆放」 | 一致，顺序策略更明确 |
| 原文序 | 给 `_filter_by_distance` 加可选 `ids` 参数 | **没动 `retrieval.py`**；改成在 `llm.py` 里用 `full_text.find(chunk)` 定位 | 见下 |
| 老索引重建 | 新增 `scripts/reindex_all.py` | 已加（默认干跑，`--apply` 才动手） | 一致 |
| `MAX_DISTANCE` | 按实测重标 | **实测后决定不动**，保持 0.55 | 证据不支持改，见上面结论 3 |

**为什么要动 `pdf_ingestion.py`（计划外）**：`split_text` 在拼装时会把「上一块的
尾部 overlap」拼到新块开头。当一段没有标点的长文本被硬切成恰好 `chunk_size` 长的
片段时，`overlap + 片段` 会达到 `overlap + chunk_size`——即使把 `CHUNK_SIZE` 缩到
480，仍会切出 ~580 字的块，**照样被 512 窗口截断**。修法是：这一步拼装如果超过
`chunk_size`，就放弃这段 overlap（硬切本身已经保留了重叠，内容不会断）。
`tests/test_pdf_ingestion.py::test_no_chunk_exceeds_chunk_size` 就是钉这个的。

**为什么原文序没用 ids（偏离计划）**：ids 确实能还原块在原文里的位置，但预算装配
发生在 `llm.py`——必须在「预算耗尽前」决定留哪些块。如果让 `hyde_retrieve` 先按
id 排成原文序，再让 `llm.py` 按顺序取前几块，就会变成「优先留文档靠前的块」，
而不是「优先留最相关的块」，那是更糟的取舍。所以顺序策略改成：**相关度序决定留谁，
原文序决定怎么摆**；位置用 `full_text.find(chunk)` 取，索引与当前全文不一致而找不到的块
排到最后、内容不丢（有单测钉住）。

## 怎么读这些数字

- **recall@5**：正样本里答案片段出现在前 5 个 chunk 的比例。掉下来通常意味着切片变差、
  阈值过严或排序被打乱。
- **MRR**：首个命中位次倒数的均值。比 recall 更敏感地反映「答案被排到后面去了」。
- **负样本误召回率**：本该返回空却返回了内容。它直接对应「答非所问」，比 recall 更值得盯。
- **超过窗口的 chunk 数**：这是 P1 的直接证据；`2/6 → 0/9` 就是这个改动的全部理由。
- **建议 MAX_DISTANCE**：只在正负分离带清晰时才有意义。合成语料上它已经**分不开**了，
  所以这一列只能用来判断「阈值有没有卡到正样本」，**不能**用来给线上定值。
- **先看这次评测到底在测哪条路**：`--no-hyde` 模式下 query 是短问句，向量距离可能整体
  落在阈值之外而走**关键词兜底**，此时指标反映的主要是 2-gram 打分、而不是向量质量。
  现在不必再从日志里推断：每条样本在 JSON 里都带 `path`（`vector` / `keyword`），汇总里的
  `keyword_fallback_samples` 就是兜底总数，`--verbose` 的逐条明细也会标出来。

## 本基线不覆盖什么

- 不覆盖真实 HyDE 路径的质量（默认 `--no-hyde` 是刻意的：先隔离「切片/阈值/排序」变量，
  且不花 API 额度）。要看 HyDE 请显式 `--hyde`。
- 不覆盖多轮指代消解（`resolve_query`）——评测集都是单轮问题。
- 不覆盖生成质量（回答是否忠实于 context），只覆盖检索这一层。
- 不覆盖真实用户文档的版式差异（PDF 表格、PPTX 备注等），合成语料是纯文本。
- 不覆盖「重建索引」的耗时与真实数据规模下的表现（`reindex_all.py` 在大知识库上会重新
  嵌入全部内容，慢是已知代价）。

## 真实语料（只记数字，2026-10-06 实测）

口径：`scripts/eval_real_corpus.py` —— 只读 `state/*.json` 的 `files[].file_text`，用
`chromadb.EphemeralClient` 建临时库（不碰真实 `chroma_db/`），不落文件、不打印正文。
语料 = 4 个真实对话 / 23 个文件 / 约 29.7 万字 → **1199 个 chunk**（CHUNK_SIZE=480）；
提问 = 这些对话里用户的 **12 条真实提问**（距离为「原始查询的最佳距离」，未经阈值过滤）。

| 指标 | 值 | 备注 |
| --- | --- | --- |
| 超过窗口的 chunk 数 | **0 / 1199** | 分对话：0/61、0/39、0/1061、0/38 |
| 真实提问最佳距离（no-hyde） | n=12 · min **0.4277** · 中位 **0.4905** · max **0.5841** | **1/12（8.3%）超过 0.55** —— 那条在线上会被关键词兜底接走 |
| 无关提问代理距离（no-hyde） | n=20 · min **0.5111** · 中位 **0.5456** · max **0.6827** | **10/20（50%）超过 0.55** |
| 真实提问最佳距离（**`--hyde`，线上口径**） | n=12 · min **0.3879** · 中位 **0.4376** · max **0.5486** | **0/12 超过 0.55** —— 线上口径下阈值不再误伤真实提问 |
| 无关提问代理距离（**`--hyde`，线上口径**） | n=20 · min **0.4244** · 中位 **0.5273** · max **0.6530** | 只有 **6/20 超过 0.55**（no-hyde 是 10/20）→ 无关侧反而更容易漏进来 |

「无关提问」= 合成负样本 n01–n05 套到真实语料上，**是代理、不是真实语料的负样本**（真实语料没有 gold）。

**这些数字说明什么：**

1. **切窗那条收口了**：真实语料 1199 个块没有一个超过 512 token。P1 把 `CHUNK_SIZE` 从 600
   调到 480（外加 `pdf_ingestion` 的 overlap 兜底）之后，真实数据上不再有「尾部被 tokenizer
   静默截断」的块 —— 这是那次改动最直接的效果证据。
2. **HyDE 口径下真实提问全部落在阈值内**：0/12 超线，中位 0.4376（比 no-hyde 的 0.4905 低）
   —— HyDE 生成的「像文档的片段」与真实语料距离更近，「0.55 对真实提问偏紧」在线上口径下
   **不存在**；no-hyde 那 1 条超线正是「短问句直查」才有的现象。
3. **但无关侧在 HyDE 口径下更容易漏进来**：无关代理最小距离 **0.4244 ≤ 0.55**，20 条里只有
   6 条超线（no-hyde 是 10/20）。修好 HyDE 之后，无关提问的最近块更容易被判成「相关内容」
   喂给模型 —— 0.55 对无关提问的拦截能力是**变弱**的。而正负两侧在两种口径下都**重叠**
   （HyDE：正 max 0.5486 > 负 min 0.4244），**没有任何一组数字支持给 0.55 换一个新值**：
   保持 0.55；真正的出路是相对阈值 / reranker，而不是拍一个新的绝对阈值。

**口径本身有个坑（同日发现并修复）**：`_generate_hyde` 里写死的 `max_tokens=200` 会被
`deepseek-flash` 的推理过程吃光（实测 `finish_reason=length`、`reasoning_tokens=200`、
`content` 空串），空内容又被 `or question` 静默兜成原问题 —— 也就是说**「HyDE 检索」自模型切到
`deepseek-flash` 起一直是关着的**，此前所有标着「HyDE 口径」的数字其实都是 no-hyde。修法：
这一次调用显式 `extra_body={"thinking": {"type": "disabled"}}`（HyDE 只要一段像文档的片段、
不需要推理链，cap 保持 200），并给空内容补上 WARNING；`scripts/eval_real_corpus.py --hyde`
增加了自检，生成的文本与原问题相同时直接中止。上表两条 HyDE 行是修复**之后**重测的。

## P2（同日）：让引用可核验

背景：2026-07-24 那套 `sources` SSE 事件 + 前端引用渲染是被**删掉**的，原因是**引用不准确**。
所以这一批不碰前端，只修根因 —— 让「块 → 来源」在数据层是真的，前端显示等后端准了再说。

| 改动 | 说明 |
| --- | --- |
| `load_pdf` 加页分隔符 | 每页输出 `=== 第 N 页 ===`（与 pptx 对齐）；纯图片页不出页头、页码仍按真实页序。顺带修掉「跨页文字直接首尾相连粘成一句」的老毛病 |
| `split_files(files)` | **按文件、按节切片**（节 = 一页 / 一个工作表），块永不跨文件、也不跨节；meta = `{file_name, chunk_index, section}` |
| `_rebuild_collection` | 改用 `split_files` 建索引，并把 meta 写进 Chroma 的 `metadatas` |
| `hyde_retrieve_hits()` | 检索结果带来源 `(文本, meta)`；旧 `hyde_retrieve()` 保持签名做薄封装，老调用方不用改 |
| `retrieve_and_build_context(files=…)` | 每块前面加 `【来源：文件名 · 第 N 页】`，标签本身也计入 context 预算 |
| `prompts.py` | 要求模型引用【来源：…】给出的文件名/页码，不再自己数「根据背景第 X 段」 |
| 老索引兼容 | 没有 `metadatas` 的老块 → 标「来源未标注」，不崩、也不编造 |
| 评测 | 改用 `split_files`，新增**文件归属正确率**（命中块的文件是否等于 `expect_files`，这个字段此前标了却一直没用上） |

**为什么按「节」切、而不是按整篇切完再补页码**：块与页之间必须有**确定**的对应关系。
按整篇切出来的块可能横跨两页，这时贴任何一个页码都会说错 —— 那正是上一版引用功能被删的根因。
代价是短页 / 短幻灯片会切成更小的块（一页一块），所以这一批必须看评测数字；
这也正是 P0 那份基线存在的意义。

**P2 实测（2026-10-06 19:37，与 P1 的 `docs/baseline-p0-after.json` 对比）：**

| 指标 | P2 前（`baseline-p0-after.json`） | P2 后（`baseline-p2.json`） |
| --- | --- | --- |
| 文件归属正确率 | 无数据（那时还没有元数据） | **1.000（30/30）** |
| recall@5 | 1.000（30/30） | **1.000（30/30）** |
| MRR | 0.961 | **1.000** |
| 负样本误召回率 | 0.000（0/5） | **0.000（0/5）** |
| 超过 512 token 的 chunk | 0/8 | **0/9** |
| chunk 数 | 8 | 9 |

**结论**：按「文件 + 节」独立切片（块变小、变多）**没有伤害检索** —— recall@5 保持满分，
MRR 反而从 0.961 升到 1.000（30 条正样本全部落在 rank 1），负样本误召回率仍是 0。
「文件归属正确率 30/30」说明来源元数据从建索引到评测统计这条链路是通的。

**section 级指标（同日补齐，`docs/baseline-p2-section.json`）**：上面那版只覆盖了「文件」
那一层 —— 6 个语料文件全是 `.md`，没有结构标记，所以 `section`（页码/工作表名）那条路径

调用），上表的距离带是修好之后重测的。

- 新上传的 PDF，抽取文本里会带 `=== 第 N 页 ===` 页头（预览的「抽取文本」里能看到，与 pptx/xlsx 一致）；

## reranker（跨编码器精排，2026-10-06 立项并实测）

**动机**：修好 HyDE 之后暴露出「无关问题被强行作答」（合成评测误召回 0/5 → 2/5，`n01`/`n03`；
真实语料无关代理 20 条只剩 6 条超阈值）。正负**距离**带在两种口径下都重叠，任何绝对阈值都
分不开 —— 根因是双编码器只比较「各自编码后的向量距离」。跨编码器把 query 和块**拼在一起**过一遍
模型、给出逐对匹配分，是唯一能分开这个的方向。

**选型与代价**（按仓库规矩逐项写清）：

| 维度 | 值 |
| --- | --- |
| 模型 | `BAAI/bge-reranker-base`（与现有 embedding 同族） |
| 许可证 | **MIT**（已排除 `jinaai/jina-reranker-v2-base-multilingual`：CC-BY-NC-4.0 非商业） |
| 参数 / 体积 | 278M / **1.11 GB**（`model.safetensors`） |
| 新依赖 | **无** —— `sentence-transformers` 自带 `CrossEncoder` |
| 首次下载 | 一次性。**HF 通道实测只有 34–245 KB/s（75–90 分钟，且 `huggingface_hub` 会卡在 0 字节）；ModelScope 同源仓库实测 12.6 MB/s（约 90 秒）**，建议国内先拉到本地目录再让 `RERANK_MODEL` 指过去 |
| 运行时延迟 | **CPU 3.9 s/次**（20 候选，单对约 280ms）—— 决定默认值的关键数字 |
| 离线可用性 | 权重落地后完全本地（实测 `HF_HUB_OFFLINE=1` 可加载） |

**接线**：向量取 `RERANK_CANDIDATES=20` 个候选（**开了重排就不再用 `MAX_DISTANCE` 先砍**），
用**原问题**（不是 HyDE 文本 —— 跨编码器的训练分布是 question → passage）逐对打分，留
`RERANK_TOP_N=5` 且 `score >= RERANK_MIN_SCORE`；命中为空才走关键词兜底。模型不可用/离线/打分
抛错一律 WARNING + 退回距离阈值（绝不把一堆远块原样塞给模型）。

**正负分数带**（合成语料、no-hyde 的 top-20 候选、原问题打分）：正样本 gold 分数
min **0.0284** / 中位 **0.9636** / max 0.9993；负样本最高分 min 0.0019 / 中位 0.0084 /
**max 0.0738**。判别力远好于距离，但严格中点规则报「分不开」—— 因为有**一条**正样本只有
0.0284。所以阈值改用「跑评测比指标」标定：0.1 与 0.3 两档指标完全相同，取更严格的 **0.3**。

**前后对照（合成评测，41 条样本）**：

| 配置 | recall@5 | MRR | 文件 / section 归属 | 兜底 | 负样本误召回 |
| --- | --- | --- | --- | --- | --- |
| no-hyde，无重排 | 1.000 | 1.000 | 1.000 / 1.000 | 7/41 | 0.000 |
| **HyDE，无重排** | 1.000 | 0.958 | 1.000 / 1.000 | 3/41 | **0.400（`n01`、`n03`）** |
| no-hyde + 重排 0.3 | 1.000 | 1.000 | 1.000 / 1.000 | 6/41 | 0.000 |
| **HyDE + 重排 0.3（线上口径）** | **1.000** | **1.000** | **1.000 / 1.000** | 6/41 | **0.000** |

**结论**：线上口径下重排把「无关问题被强行作答」**完全堵住**（5 条负样本全部正确返回空），
同时 recall / MRR / 归属一分不掉（MRR 还从 0.958 回到 1.000）。

**但默认值定为 OFF**（`RERANK_ENABLED=0`）：约定是「误召回压到 0/5 **且** 中位延迟 ≤ ~1.5s
才默认开」，实测 **3.9 s/次** 远超门槛。要开就显式 `RERANK_ENABLED=1`（并用 `RERANK_MODEL`
指向本地权重目录）。想两头兼顾的后续方向：减少 `RERANK_CANDIDATES`，或换量化 ONNX 跑
（`onnxruntime` 已在依赖里，不必新装）。

> 「0/5」看着很漂亮。同一天把负样本扩到 **23 条**（15 远域 + 8 域内无答案）后，真实情况

> 「0/5」当结论**，以「负样本分两类」那一节的数字为准。

## 双路融合（原问题 + HyDE，2026-11-05）

**动机**：单探针只能跟一种「问题改写」走。HyDE 会把短问句揉成一段「像文档的片段」，关键词在
长句里被稀释后，那一侧偶尔整段超阈值；反过来，纯原问题直查又会丢掉「用户没写出来的术语」。
两条路互相补位，但**结论必须由实测决定** —— 融合有两种完全不同的闸门口径：

- union：任一路「近」就算命中（召回优先）；
- intersect：**两路都得近**才算命中（精度优先）。

--hyde-cache 是这次能比得干净的前提：两轮复用**同一批**假设文本（否则比的是大模型的
随机性 —— 同一份配置连跑两次 MRR 0.972 / 0.958）。

### 结论与默认值

1. **intersect 是这次真正的收获**：合成语料两批都把负样本误召回压到 **0/5**，recall / 归属
   一分不掉、MRR 反而升（0.972 → 1.000 / 0.986）；真实语料无关代理漏进 **17/20 → 13/20**。
   这是 reranker 那条 0/5 的效果，**但零新依赖、不用下 1.1GB 权重、延迟只多 17 ms**。
2. **union 不是**：两批样本里误召回一条都没降（2/5、1/5 原封不动），只在样本1带来 +0.014 MRR。
   它救回了真实语料里那条提问（11/12 → 12/12），但代价是代理漏进从 13 涨到 15。
3. **默认值 = 开 + intersect**：按「误召回 0/5 且中位延迟 ≤1.5s 才默认开」那条约定，它过线
   （reranker 因 3.9 s 没过）。**副作用必须记住**：闸门收窄后有 **7/41** 样本落进关键词兜底
   （改造前 3–4 条），那些样本的分数是 2-gram 词面分、不是向量语义 —— 判读指标时要按 path 拆开。
4. **延迟**：41 条样本 1.1 s → 1.8 s（同一批假设文本、不含 API 时间），即**每问约 +17 ms**；
   多出来的就是第二条探针的 embedding。
5. **诚实边界**：负样本只有 5 条，「0/5」的证据强度有限；真实语料的无关代理是**合成问题套到
   真实正文上**，不是真实语料的真负样本。真实提问侧 intersect 与改造前同为 11/12（union 是 12/12），
   所以「精度优先」这个取舍是对真实数据有代价的 —— 想换回来只改 FUSION_GATE=union。

## 负样本分两类（2026-11-05 补测，59 条 = 36 正 + 15 远域 + 8 域内）

**为什么要补**：原来只有 5 条负样本（量子纠缠、火星探测器、莫扎特、光合作用、板块构造），
全是**远域**且被测试约束成「与语料零词面重叠」。样本少且太容易，误召回 0/5 这种结论经不起
推敲。补测按产品里真实的两种失败模式拆开：

- **far（远域，15 条）**：与语料零词面重叠（大提琴泛音列、台风登陆点预报误差…），
  考「会不会被阈值外的噪声拉进来」；
- **adjacent（域内但无答案，8 条）**：**故意**与语料有词面重叠（年会抽奖的奖品预算走谁的审批、
  婚假需要提交哪些证明材料…），考「看起来像就作答」——这才是用户真正会踩的坑。

两条相反的纪律都用测试钉住：far 必须**零** 2/3-gram 重叠，adjacent 必须**有**重叠
（	ests/test_eval_retrieval.py），否则这两类样本会互相伪装。

| 配置 | recall@5 | MRR | 归属 | 关键词兜底 | 远域误召回 | 域内误召回 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| HyDE，关融合（改造前） | 1.000 | 0.972 | 1.000/1.000 | 4/59 | **11/15（73%）** | **8/8** | 19/23（83%） |
| HyDE + union | 1.000 | 0.986 | 1.000/1.000 | 4/59 | **11/15** | **8/8** | 19/23 |
| **HyDE + intersect（默认）** | **1.000** | **1.000** | **1.000/1.000** | 15/59 | **2/15（13%）** | **8/8** | **10/23（43%）** |
| no-hyde（参照，免费） | 1.000 | 1.000 | 1.000/1.000 | 15/59 | **2/15** | **8/8** | 10/23 |

### 三个结论

1. **误召回的元凶是 HyDE 本身，不是阈值**：逐条看 path，**19 条误召回 100% 走向量路径**，
   一条都不是关键词兜底。HyDE 一定会编一段「像语料」的假设文本，所以任何提问（哪怕问大提琴）
   都能被它拉到某个块附近。真实语料那轮「无关代理 17/20 漏进」是同一个机制。
2. **intersect 把 HyDE 的副作用压回 no-hyde 水平**：远域 11/15 → **2/15**，而 no-hyde 也是 2/15
   —— 也就是说「两路都得近」这个闸门把 HyDE 拉回来的那些假近邻全部过滤掉了，同时保住了
   HyDE 在**真实提问**上的距离优势（真实语料 12 条提问的 HyDE 侧最佳距离中位 0.4401 < 原问题侧
   0.4905）。副作用是 15/59 的样本改由关键词兜底处理（4/59 → 15/59）。
3. **域内无答案 8/8 全误召回，闸门和阈值都挡不住**：它们的原问题与语料词面/语义都近，两条
   探针都「近」，MAX_DISTANCE=0.55 也判它近。这不是调参能解决的，需要**可答性判断**
   （重排分下限 / LLM 判定「context 里有没有答案」/ 显式拒答）。这是本项目的下一个真问题。

## 可答性判断（2026-11-05 实现并实测）

**它解决什么**：上一节那个「域内 8/8 全被作答」的问题。所有**相关性**信号都失效了 ——
阈值扫描、兜底命中强度、融合闸门全是「既漏又误杀」。于是不再问「有多相关」，直接问模型
「这段材料能不能回答这个问题」。

**实现**：`src/answerability.py`，在 `retrieve_and_build_context` 返回非空之后、生成回答之前调用；
输出格式强制成 `能：<原文依据>` 或 `不能`（`temperature=0`、`max_tokens=32`、**关思考**），
判「不能」就走已有的「未找到相关内容」拒答路径（400，提问不入库）。

### 关键发现：判定必须**要求给出原文依据**

同一批数据、同一套检索，只改判定 prompt：

| 判定提示词 | 域内负样本拦下 | 正样本误杀 | 判定耗时 |
| --- | --- | --- | --- |
| 只答「能 / 不能」（第一版） | 8/8 | **2/36（`q16`、`q29`）** | 0.72 s |
| 加一句「措辞不同不算问题」 | 8/8 | 1/36（`q29`） | 0.72 s |
| **要求输出 `能：<原文依据>`（采用）** | **8/8** | **0/36** | **0.78 s** |

两版误杀的共同原因很好理解：`q16`「工单超时没人处理会怎样」对原文「工单超过约定响应时效未响应
的…」、`q29`「窑温是怎么升上去的」对原文「窑温通常分三段缓慢抬升」—— **语义相同、措辞不同**，
只问「能不能答」时模型按字面判了「不能」。**逼它摘一句原文**之后，两个都判对了。

### 最终效果（59 条，默认口径：HyDE + 融合 intersect + 可答性判断）

| 指标 | 结果 |
| --- | --- |
| 域内负样本被拦下 | **8/8** |
| 远域负样本被拦下 | 2/2 |
| 正样本被误杀 | **0/36** |
| 判定不可用（按老行为作答） | 0 |
| 判定耗时 | 平均 0.75–0.78 s / 次（46 次调用） |

两批复测：同一批假设文本再跑一次、以及换一批独立假设文本（`hyde-cache2.json`）各跑一次，
**结果完全一致**（8/8、2/2、0/36）。也就是说：**域内误召回从 8/8 降到 0/8，代价是每条能检索到
内容的提问多 0.78 s**（比 HyDE 那次调用还短，因为它关思考且只要一行输出）。

### 三条工程纪律（都有用例钉着）

1. **要求给出原文依据**：只让模型答「能/不能」会系统性误杀「措辞不同但同义」的正样本（2/36 → 0/36）。
2. **解析认不出就返回 `None`，不猜「不能」**：`parse_verdict` 先判「不能」再判「能」（顺序反了会把
   所有否定判成肯定），认不出的内容一律 `None`。
3. **任何故障都不许堵死问答**：缺 `API_KEY`、调用失败、`content` 为空串（推理模型吃光预算的老坑）
   一律 `None` + WARNING，按老行为继续作答。`ANSWERABILITY_CHECK=0` 可整条关掉。

## 那 0.78 s 是怎么省掉的（2026-11-06）

上一节的可答性判断每条提问固定 **+0.78 s**。三条路试下来，最后一条直接把这次调用**删了**。

### 试过一：用距离门槛跳过判定？—— 死路

「已经很近就不用再判」听起来合理，实测不行（59 条，融合 intersect 闸门放行块里的最小距离）：

| 门槛 D（距离 ≤ D 就跳过判定） | 省掉的判定次数 | 漏网的域内负样本 |
| --- | --- | --- |
| 0.20 | 10/44 | **1**（`n18`，0.1944） |
| 0.25 | 21/44 | **2**（`n18`、`n22`） |
| 0.30 | 31/44 | **3**（`n18`、`n21`、`n22`） |
| 0.35 | 38/44 | **6** |

原因：域内负样本的最佳距离（0.1944–0.4779）与正样本（0.0886–0.3617）**完全交织**，
省得越多漏得越多 —— 和不做判定的效果一样差。

### 试过二：把判定输入缩短？—— 没用

判定延迟不是 prefill 撑起来的：

| 判定看到的材料 | 平均耗时 | 中位 | 域内拦下 | 正样本误杀 |
| --- | --- | --- | --- | --- |
| 全部命中块（原始口径） | 0.78 s | 0.80 s | 8/8 | 0/36 |
| 只看 top-2 块 | 0.92 s | 0.92 s | 8/8 | 0/36 |
| 只看 top-1 块 | 1.01 s | 0.94 s | 8/8 | 0/36 |

延迟基本是**一次 API 往返**，跟材料长短无关（差异在噪声范围内，甚至反着来）。缩短输入只会
丢信息、不会更快。

### 试过三：让**生成那一次调用**自己拒答 —— 成了

`QA_SYSTEM_PROMPT_TEMPLATE` 第 1 条本来就是「如果【参考背景】中没有明确答案，请直接说
『背景中没有提到相关内容』，不要编造」。那就干脆不另发判定调用，量它自己管不管用
（`scripts/measure_inline_abstention.py`，46 条有内容的样本全部真跑一遍生成）：

| 口径 | 域内负样本正确拒答 | 远域负样本 | 正样本被误拒 | 额外调用 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 独立判定（上一节） | 8/8 | 2/2 | 0/36 | **+1 次** | +0.78 s |
| **inline：让生成自己拒答** | **8/8** | **2/2** | **0/36** | **0** | 0 |

生成侧实测：中位 **1.30 s** / 首 token 中位 **1.09 s**（46 条）。也就是说带判定的路径 ≈
0.78 + 1.30 ≈ 2.1 s，**inline 只要 1.30 s**。

而且拒答文案比 400 更有用 —— 它会说清楚「材料只写了什么、所以答不了」：

> 背景中没有提到「数据库主从切换」的演练步骤。参考背景只涉及数据备份与恢复规范，其中与演练
> 相关的内容是「恢复演练」，但演练场景为：单表误删、整个数据库损坏和机房级故障三种场景，
> 并规定每半年至少组织一次恢复演练…文档中并未提及主从切换的演练步骤或流程。

### 结论与默认值

- **`ANSWERABILITY_CHECK` 默认改为 0**（inline 拒答）：质量与独立判定一模一样（都是 8/8、0/36），
  但省掉每条提问 0.78 s 和一次调用。
- 独立判定保留为**严格模式**（`ANSWERABILITY_CHECK=1`）：判「不能」直接 HTTP 400「未找到相关内容」、
  不生成任何回答 —— 需要「不许为不可答问题产生任何回答」的场合才开。
- 两次口径的取舍点很明确：**inline 少 0.78 s 且拒答更详细；严格模式省掉为不可答问题生成的那 1.3 s**。

服务日志里**没有任何「可答性判断」记录** —— 确认这条路径上真的不再多发那次调用。

### 这个方案的新问题

1. **拒答被当成普通回答**：前端会把它渲染成一条正常消息（还带 sources），而不是原来的 400 提示。
   语义上没问题（用户照样知道「库里没有」），但如果产品上要求「拒答必须显式标注」，就得在
   前端加个判定或让后端推一个 `refused` 事件。
2. **`looks_like_abstention` 只是测量用的启发式**（看开头 120 字），生产路径不依赖它 —— 一旦
   要拿它做 UI 分支，就得换成更硬的契约（让模型输出结构化前缀）。
3. **部分可答的提问没测**：这 59 条要么全答得上、要么完全答不上。用户问「两个问题、其中只有一个
   在库里」时 inline 会不会整段拒答，需要专门的样本。

## 拒答要能被看见：`refused` 事件（2026-11-07）

上一节把独立判定删掉之后，出现一个新问题：**拒答被当成普通回答**（HTTP 200 + 文案 + sources），
前端没法把它和正常回答区分开。这一节把这事儿收口。

### 为什么不能靠「文案启发式」

最省事的做法是看回答里有没有「没有提到」这类词 —— 但正常回答里引用到这几个字就会被误标
（比如用户问「这个标记怎么用」）。所以改成**结构化契约**：

1. `prompts.QA_SYSTEM_PROMPT_TEMPLATE` 第 1 条要求：答不出时必须以 `prompts.REFUSAL_MARKER`
   （`【无答案】`）**开头**，然后简述材料里有什么、为什么不足；
2. 服务端在流式**开头**缓冲判定（标记可能被拆在两个 token 里：`【无答` + `案】`），判成拒答就
   推一条 `{"type":"refused"}` 事件、把标记从正文里剥掉、落盘 `refused: true`；
3. 前端只认这个事件/字段（`d.type==='refused'` / `message.refused`），不猜文案，渲染成
   `⚠️ 知识库里没有能回答这个问题的内容` 的小标签。

判定三态（`llm.refusal_state`）是关键：`True` 拒答 / `False` 正常 / `None` **还看不出来**。
一拿到首个 token 就下结论，会把 `【无答` 误判成正常回答。

### 换了提示词之后必须复测（模型听不听话）

| 口径 | 域内负样本正确拒答 | 远域 | 正样本被拒 | 生成中位耗时 |
| --- | --- | --- | --- | --- |
| 旧提示词（只说「背景中没有提到相关内容」） | 8/8 | 2/2 | 0/36 | 1.30 s |
| **新提示词（要求 `【无答案】` 开头）** | **8/8** | **2/2** | **0/36** | 1.72 s |

10 条有内容的负样本回答**全部**以 `【无答案】` 开头（逐条看过原文），契约成立；
36 条正样本一条都没写这个标记。耗时从 1.30 s 涨到 1.72 s 属于 API 波动（同一批假设文本、
同一套检索），不是提示词变长导致的 —— 不过要记住这个量级，别把它当基线。

### 端到端验证

- `tests/test_refusal.py`（16 条）：三态判定、markdown 加粗的标记、**跨 token 拆开**的标记、
  正常回答一个字节不改、正文中间的标记不算拒答、只回标记本身时的空回答不落空消息；
- `tests/test_frontend.py` 三条静态守卫：接住 `refused` 事件、`refused` 跟着消息落盘、
  标签只用 `createElement` + `textContent`；
- 真实 uvicorn 冒烟（8099 + 临时目录）：能答 → `refused=False` + 正常回答；
  「恢复演练要请哪些人参加」→ `refused=True`，正文里**没有**标记残留；
  落盘核对 `[('assistant', False), ('assistant', True)]` —— 刷新后仍能渲染成拒答。

### 拒答不挂来源（2026-11-07 补）

最初拒答消息也会带上 `sources`（「查过哪些文件」）。**改掉了**：既然材料答不了这个问题，
把来源贴给用户只会让人以为这些文件就是答案出处。做法是把 `sources` 事件**推迟到判定之后**
再推 —— token 本来就在缓冲，正常回答仍然「sources 先于第一个 token」到达，顺序契约不变；
判成拒答则既不推也不落盘。

| 场景 | sources 事件 | 落盘 |
| --- | --- | --- |
| 正常回答 | 有（第一个 token 之前） | `sources` + 正文 |
| 拒答 | **无** | 只有 `refused: true` + 正文（标记已剥） |

验证：`tests/test_refusal.py` 的 `test_refusal_carries_no_sources` /
`test_normal_answer_still_pushes_sources_before_the_first_token`；真实 uvicorn 冒烟核对
`落盘 (refused, has_sources) = [(False, True), (True, False)]`。

### 拒答时报「已检索几个文件」（2026-11-08 补）

拒答不挂来源是对的，但「查过什么」全丢掉也不对：用户需要知道「我的文件到底被看了没有」。
所以拒答事件多带一个**计数**：

- `refused` 事件：`{"type": "refused", "searched_files": N}`；
- 落盘：`refused: true` + `searched_files: N`（刷新后标签还在）；
- 前端标签：`⚠️ 知识库里没有能回答这个问题的内容（已检索 N 个文件）`。

**只给计数、不给文件名**：文件名跟「答案出处」绑在一起会误导人（那正是当初去掉 sources 的原因），
而计数只回答「看了没有、看了几份」。N 按**文件名**去重（不是「文件 + 页」——用户关心的是文件，
不是看了几页），取自装配 context 时真正用到的那几个块。

真实 uvicorn 冒烟（上传 2 个文件，问「恢复演练要请哪些人参加」）：`refused` 事件
`searched_files=1`（只有备份规范的块进了 context）、无 `sources` 事件；落盘
`(refused, searched_files, has_sources) = (True, 1, False)`。

### 前端渲染测试（2026-11-08 补，补掉了原来「没有 e2e」这条）

静态守卫（`tests/test_frontend.py`）只能证明「index.html 里有这行」，证明不了「渲染出来是什么样」。
所以加了 `tests/test_frontend_render.py`：

- 从 `index.html` 里**抽出真实的函数源码**（`buildRefusedTag` / `showRefusedTag`，按花括号配对切），
- 用 Node 内置 `vm` 跑，配一个极小的 DOM 替身（`createElement` + 节点树 + `querySelector`），
- 断言：无计数时不出现空括号、有计数时是「（已检索 2 个文件）」、**非数字/undefined 一律不加**、
  `showRefusedTag` 重复调用不叠第二个标签、以及**拒绝使用 innerHTML**（替身的 setter 直接抛错）。

三条纪律：**不引 npm 依赖、不装 headless 浏览器**（前端本来是零依赖原生 JS，测试不该给它加工具链）；
本机没有 `node` 时整组 `pytest.skip`（CI 的 ubuntu runner 自带 node，会真跑）；
切不出函数源码就**大声报错**，绝不返回半截——半截会让断言假通过。

反向对照：把 `buildRefusedTag` 里那句临时改成 `tag.innerHTML = text`，4 条用例全部变红
（替身抛错），还原后全绿。

## 部分可答的提问（2026-11-08）

**为什么补这一类**：此前 67 条里要么全答得上、要么完全答不上，而产品里最常见的形状是
**一个问句里一半有答案、一半没有**（「年假有几天，病假工资怎么算」）。这种样本此前一条都没有，
所以「整条回答被标成拒答」这种**过度拒答**根本测不出来。

### 样本与判定口径

`tests/fixtures/eval_queries.json` 新增 `kind: "partial"` 8 条，字段：

- `answer_terms`：可答部分的关键事实，**必须真的出现在语料里**（否则这条样本永远「答不到」）；
- `absent_terms`：语料里没有的那半个问题的主题词，**必须真的不在语料里**（否则就成了「其实答得上」）。

两条都用测试钉住（`test_partial_answer_terms_really_appear_in_corpus` /
`test_partial_absent_terms_really_are_absent`）。回答按五桶分类（`scripts/measure_inline_abstention.py`
的 `classify_partial`）：

| 桶 | 含义 |
| --- | --- |
| `refused_all` | 整条消息被标成拒答，可答部分也没答 —— 最糟 |
| `refused_despite_answer` | 整条消息被标成拒答，但正文其实答了 —— 用户仍然看到「知识库里没有」，仍算过度拒答 |
| `answered_with_gap` | 正常作答 + 点明缺什么 —— **理想** |
| `answered_silently` | 答了可答部分，但对缺的那半只字不提 —— 有编造/含糊风险 |
| `neither` | 可答部分没答到、也没提缺口 —— 答偏了 |

### 第一版结果：5/8 过度拒答（真问题）

提示词当时只有一句话「没有答案就以 `【无答案】` 开头」，于是模型把**整条回答**都打上标记，
哪怕正文已经答对了可答的那一半：

| 桶 | 条数 |
| --- | --- |
| `refused_all` / `refused_despite_answer` | **5/8**（`p03`、`p04`、`p06`、`p07`、`p08`） |
| `answered_with_gap` | 3/8 |

看原文确认：那 5 条其实**答对了可答部分**（`p04` 明确写了「一线城市每晚不超过 600 元」），
只是整条消息以 `【无答案】` 开头 → 前端会显示「知识库里没有能回答这个问题的内容」，属于**标记语义错了**：
它该表示「整条答不了」，不是「有一半答不了」。

### 提示词改了两处，四项指标同时达标

1. 明确三档：完全没涉及 → 写标记；**只答得了一部分 → 先正常作答并标来源，再说明缺哪部分，
   不许写标记、不许因此丢掉能答的部分**；能完整回答 → 正常回答。
2. 划清「相关话题 ≠ 回答了用户问的那件事」（用户问「能不能折成工资」，材料只写「逾期作废」，
   算完全没涉及）。

| 指标 | 改前 | **改后** |
| --- | --- | --- |
| 部分可答 · 过度拒答 | 5/8 | **0/8** |
| 部分可答 · 答了可答部分 + 点明缺口 | 3/8 | **8/8** |
| 域内负样本正确拒答 | 8/8 | **8/8** |
| 远域负样本正确拒答 | 2/2 | **2/2** |
| 正样本被误拒 | 0/36 | **0/36** |
| 生成耗时中位 | 1.54 s | 1.55 s |

真实 uvicorn 冒烟（「全量备份保留多久？异地机房怎么切换？」）：`refused=False`，
答到「30 天」并注明来源，另起一段说明「异地机房…材料里没有涉及」——正是想要的样子。

### 顺带修掉的标注错误

`p08`（青花瓷）第一次被判成「可答部分也没答到」，看原文发现**是我的标注错了**：问题问的是
「为什么要控制降温速度」，我给的 `answer_terms` 却是「分三段缓慢抬升」（讲的是**升温**）。
改成「产生应力」后该项立刻归位。**标注错会让指标变成假的** —— 这也说明 `answer_terms` 必须
像 `gold_phrases` 一样被测试盯住（它现在确实被盯住了）。

### 还没测的

1. **三件以上的复合问题**（A、B、C 三问，只有一个能答）—— 目前只有「两问」样本。
2. **缺口在中间**（问题 A、B、C 里只有 B 没有）—— 模型可能只答前后两段、漏掉中间的缺口提示。
3. **多轮里的部分可答**（上一轮问了一半、这一轮补问）—— 指代消解 + 拒答标记的交互没测。
