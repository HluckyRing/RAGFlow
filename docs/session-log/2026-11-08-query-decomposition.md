## 第一轮：每问分路检索的对照实验

### 为什么是它

上一篇的结论是「`top_k` 不是杠杆」（覆盖@5 = 覆盖@10，未覆盖子问的目标片名次双峰：第 1 附近
或 20 名开外）。名次在 20 名开外说明**整句一起查的时候那一问根本没被当回事** —— 一句复合问句
被压成一个向量，几件事在向量空间里互相拉扯。

### 三臂设计（只换「怎么把预算分给各问」）

| 臂 | 做法 | 检索次数 |
| --- | --- | --- |
| `merged` | 现状：整句一次检索 | 1 |
| `interleave` | 每问各查 `budget` 条，**轮流分名额**（先每问第 1 名，再第 2 名…），截到 budget | = 子问数 |
| `rrf` | 每问各查 `budget` 条，按名次 RRF（与线上 `_rrf_fuse` 同口径），截到 budget | = 子问数 |

两条纪律让对照成立（都有测试钉住）：**上下文预算必须一样**（否则赢的是 token 预算）、
**分母必须一样**（都是「单问基线命中的子问」，换分母等于换了一批题）。`merged` 臂由新代码路径
重算并与原有「覆盖@k」逐位比对，**不一致直接中止** —— 新旧数字能不能比不靠人眼。

### 结果（真语料、no-hyde、seed 0、35 条样本 / 37 个可用子问）

| context 预算 | `merged` | `interleave` | `rrf` |
| --- | --- | --- | --- |
| 2 块 | 29.7% | **54.1%** | 48.6% |
| 3 块 | 37.8% | **73.0%** | 70.3% |
| 5 块 | 45.9% | **81.1%** | 81.1% |
| 10 块 | 45.9% | **89.2%** | 83.8% |

四条结论：① 同一份 5 块预算 45.9% → 81.1%，样本级全覆盖 44.0% → 84.0%；② **分路@2（54.1%）就
打赢整句@5（45.9%）**，预算不是瓶颈、「怎么花」才是；③ 分配口径是**二阶因素**（预算 ≥ 子问数时
两臂逐样本完全一致，只有预算紧张时才分道）；④ 它量的不是「检索变好了」，而是**「整句合并丢掉了
多少」** —— 分母本身由同一把检索器定义，所以分路臂在严格分母上 100% 是结构性的，有信息量的是
「29 条单独检索明明找得到的子问，整句合并丢掉了 13 条（44.8%）」。

## 第二轮：修两把量尺（上一轮留下的）

1. **「锚点可见」会跨文件通胀**：锚点允许全语料出现 ≤2 次，分路臂每次都拿带锚点的问句去查，
   很容易把**另一份文件**里的同一句模板话捞进来 —— 这列在分路臂上直接吹到 100%。新增
   `same_file_anchor`（事实在同文件**邻居片**里 —— 切片重叠造成的口径盲区）与 `strict_cross_file`
   （跨文件捞到的，不算覆盖）。本轮实测 **0 / 7**：分路臂漏的 7 处**全是跨文件模板话**。
2. **样本级全覆盖的分母错了**：原来除以全部 35 条样本，其中 **10 条一个可用子问都没有**
   （按定义算不出「全覆盖」），等于天然记成失败。改成只数有可用子问的 25 条后，
   上一篇那个 31.4% 在同口径下是 **44.0%**。

## 第三轮：拆问（query 分解）本身

`src/decompose.py`：`looks_compound()` 廉价闸门 → 一次 LLM 调用（temperature=0、关思考、
JSON 数组契约）→ `parse_parts()` 兼容围栏/编号/项目符号/每行一问，去重、截断。

三条纪律：**只拆出一条就返回原问句**（模型的同义改写只会让检索变差，单问提问因此完全不受影响）；
**任何故障退回 `[question]` + WARNING**（缺 key/抛错/空内容/解析不出 —— 与 HyDE 静默失效对照）；
**关思考、小预算**（推理模型不吞预算）。

- 闸门：文本复合 **18/18 召回**、单问误判 1/59、多轮样本 0 触发、调用率 **22.9%**。
  第一版漏了**省略式追问**（「…，境外城市呢？」）→ 把「呢」收进疑问词后补上。纪律：
  **漏判比误判贵**（误判只白花一次 0.66 s 的调用，漏判是整套功能静默失效）。
- 真模型 19 次调用：延迟中位 **0.66 s** / p90 1.07 s；条数与 gold **18/18 相同**；单问误拆 0/12；
  解析失败 0/19；`temperature=0` 复跑逐字一致。
- 端到端（真语料，`--join-style` 三种拼法）：qmark **78.4%** / comma **81.1%** / runon **83.8%**，
  gold 分路 81.1%，整句 45.9%；平均拆出 **2.69 问**且条数与 gold 逐条相同。

## 第四轮：接进线上（默认关）

`server.chat` → `_decomposer()` → `llm.retrieve_and_build_context(..., decompose=...)` →
`llm._retrieve_hits()`，三条边界：

| 情况 | 行为 |
| --- | --- |
| 开关关 / 只拆出 1 条 | 整句检索（HyDE + 双路融合 + `intersect` 闸门），**逐位不变**，连闸门都不跑 |
| 拆成 ≥2 问 | 每问**单探针**检索（不调 HyDE，仍过 `MAX_DISTANCE` 闸门）+ 轮流分名额合并 |
| 分路一条都没捞到 | 退回整句检索 |

两个决定：**分路各问不调 HyDE**（每问都调会让延迟 n 倍，而拆问只要 0.66 s；代价是丢掉
`intersect` 的第二票，但只有「已拆成 ≥2 问」的提问才走这条路）；**合并口径只有一份实现**
（`src/hits_merge.py`，线上与评测脚本共用 —— 口径写两份必然漂）。

冒烟（on/off 各 3 次）：复合问首字中位 **3.60 s（开）vs 4.71 s（关）**，打开反而更快；
`sources` 仍先于首 token、能答的 `refused=False`、域内无答案仍 `refused` + `searched_files`
且不挂 sources。补测线上预算（10）口径：模型拆问 86.5% / 89.2%，gold 89.2%，整句 45.9%。

## 第五轮：多轮 + 复合的指代路径

形状：第二轮是复合问句，**前半是省略式追问**（「那这个规定还有效吗？」—— 主语只在上一轮里）。

| 臂 | 全部 | **省略式那一半** | 自带问句 |
| --- | --- | --- | --- |
| 现状（整句，先消解） | 53.3% | **25.0%** | 85.7% |
| 拆问分路，省略式**不消解**（对照臂） | 46.7% | **12.5%** | 85.7% |
| 拆问分路 + 逐条 `resolve_query` | 73.3% | **75.0%** | 71.4% |
| 拆问分路 + 逐条消解，**拆问带历史** | 73.3% | **75.0%** | 71.4% |

三条结论：① **光分路不补指代比现状更糟**（25.0% → 12.5%）；② **补全指代的是逐条
`resolve_query`**（纯 Python 不花 API），12.5% → 75.0%，对照臂就是用来钉死这一点的；
③ **「拆问带历史」量到 0 收益** —— 不带历史时模型把省略原样留下、随后被规则补全，带历史时
模型自己补全，殊途同归；保留它只能算**保险**（规则够不到：≥15 字 / 代词不在表里 / 指代助手
上一轮的回答），不是已证的收益。

## 第六轮：并发压测

进程内基准（120 次调用/配置）：8 并发只换来 **1.28–1.35×** 吞吐，单次延迟从 12 ms 涨到
76–85 ms —— **embedding 并发是排队不是并行**（同一模型对象 + GIL，`run_in_threadpool` 只挪
阻塞活、不多给 CPU）。但它**不是瓶颈**（8 并发下 3 问分路检索账 ≈0.26 s，同请求总时长 ≈3.9 s）。

真实 uvicorn：8 个并发请求 4.2 s 完成（串行要 17 s）→ 事件循环没被堵；开关打开在每个并发档
都不慢；**20 次请求零错误、`sources` 20/20 先于首 token、`done` 全在**。

## 第七轮：默认值定案

**判据跑之前就写死在脚本里**（`.agents/decide_decompose_default.py`），四道门：

| 门 | 判据 | 实测 |
| --- | --- | --- |
| 质量 | 复合问两件事都答到 ≥ 现状 | 87.5% → **100%** |
| 拒答 | 域外复合问 100% 拒答 | **4/4** |
| 延迟 | 首字中位增量 ≤ +0.5 s 且 p95 ≤ +1.0 s | **−0.55 s / −1.01 s** |
| 安全 | 零错误 + `sources` 顺序 + 拒答不挂来源 + 单问不误伤 | 全绿 |

方法：**ON/OFF 两个服务同时起、同一条问题交替发**（52 次请求配对比）—— 分开跑两轮会把 API
抖动当成开关的作用。四道门全过 → `DECOMPOSE_ENABLED` 默认改成 **1**。

## 这一轮的坑（八条，按严重度）

1. **量尺比模型脆（第四次）**：锚点可见跨文件通胀、样本级分母含「零可用子问」样本 —— 两次都是
   量尺的错，而不是模型/检索的错。看到数字不对，**先看原文、先查分母**。
2. **前置拒答不是 `refused` 事件**：检索全空时服务端走 HTTP 400 + 中文错误、根本不进 SSE。
   判分必须认「400 且含『未找到相关内容』= 正确拒答」，否则会把 4 个正确拒答记成 4 个错误请求。
3. **语料太小，质量门空转**：`dynamic_top_k = max(10, 文件数 × 3)`，3 个文件 6 块时预算把全库
   装下，两臂都 100%（零信息）。要 4 文件 × 8 节 ≈32 块（预算 12）才卡得住。
4. **闸门要按「漏判比误判贵」调**：省略式追问差点被静默放过 —— 误判只白花一次调用，
   漏判是整套功能对那类提问失效。
5. **别把「保险」写成「收益」**：拆问带历史实测 0 收益，文档里必须写「保险」而不是「提升」。
6. **默认值改动会顺手打破测试隔离**：`DECOMPOSE_ENABLED` 变 1 之后 `test_chat_flow` 会顺着
   `server._decomposer()` 真的去调大模型 —— 已按 reranker 同款加 autouse 隔离。
7. **并发不等于并行**：`run_in_threadpool` 只把阻塞活挪出事件循环，不会多给你 CPU；
   「每问多 n 次 embedding」在 CPU 上是排队的，报延迟必须按 n 倍算。
8. **pwsh 里套多行 Python 又炸了一次**（引号被吃）—— 规矩不变：超过两行的 Python 一律写进
   `.agents/*.py` 再跑。
