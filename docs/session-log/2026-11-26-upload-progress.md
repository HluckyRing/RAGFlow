# 2026-11-26 上传进度条：真实阶段 + 真实百分比

> 上一刀把删除从 3 分钟压到 0.08 s，剩下的手感问题就是**上传没有进度**：250 块要 13–27 s，
> 界面上只有一句静态的「仍在解析中…」，用户分不清是卡死还是在干活。

## 一、为什么不是「前端自己算一个假的百分比」

上传的时间几乎全花在**服务端**：解析文件 → 切片 → 逐批 embedding。前端唯一知道的只有
「请求还没返回」。所以假进度条只能靠猜（按时间递增那种），迟早会在慢语料上跑满却还没结束。
这轮改成**后端上报真实阶段**：

| 阶段 | 含义 | 前端怎么显示 |
|---|---|---|
| `parse` | 正在解析第 `done`/`total` 个文件 | `解析文件 2/3：第2章.pdf`，占前 30% |
| `index` | 切片完成，正在 embedding 第 `done`/`total` **块** | `建立索引 128/160 块（12.4s）`，占后 70% |
| `done` | 收尾（条目随后删除） | 100%，600 ms 后淡出 |

拿不到 `total`（还在切片）时显示**不确定态**（来回滑动的条），绝不假装百分比。

## 二、怎么做的（一次请求 + 轮询，不引入任务队列）

上传接口本来就是同步的（同步保证「返回即落盘」这个语义），为进度改成后台任务队列会带来
任务状态、失败重试、清理、并发上限一堆新问题。这里的做法是**最小侵入**：

1. 前端生成 `upload_id` 随 multipart 一起发；
2. 后端在内存表里记阶段（`_progress_update`），上传结束时**删条目**（`_progress_done`，`finally` 保证）；
3. 前端每 400 ms 轮询 `GET /api/upload/progress?session_id=&upload_id=`；
4. `_rebuild_collection(conv, progress=...)` 每写完一批 64 块就回调一次 —— 这是最耗时的一段，
   必须有进度。

内存表带 TTL（300 s）顺手回收，避免失败请求留下垃圾条目。

## 三、踩到的真竞态：第一帧就是 404

第一版前端「遇到 404 就停止轮询」（想着任务结束/过期才会 404），结果实测**轮询帧数 0**：
第一次轮询往往比后端建条目更早（POST 还在路上），于是前端一帧都没拿到，永远停在「准备中…」。

改法：**错误分支不终止轮询**，循环只由调用方（上传成功/失败时 `stopPolling()`）收起。
老服务端没有这个端点时也只是安静地打几轮空请求，不影响上传。

> 这个 bug 是变异检查逼出来的：把「前端不发 upload_id」改掉时测试**全绿**，因为守卫断言的
> 是「源码里出现过 upload_id」，而它出现在**注释**里。收紧成断言
> `form.append('upload_id', uploadId)` 之后才真红。

## 四、实测（真实容器，26 万字 / 160 块）

```
上传 200  耗时 27.6s  轮询帧数 99
  parse    1/1
  index    0/160
  index   64/160
  index  128/160
  index  160/160
```

前端看到的是：`解析文件 1/1` → `建立索引 0/160` → 每 64 块跳一次 → 100% 淡出。

## 五、判据与结果

| # | 判据 | 结果 |
|---|---|---|
| 1 | 阶段真的上报（parse 与 index 都在），index 的 total 是真实块数 | 单测（打桩 spy） |
| 2 | 上传结束后条目被删（不留垃圾） | 单测 |
| 3 | 进度端点有**归属校验**（别人的任务查不到，403） | 单测 |
| 4 | 未知 upload_id → 404（前端据此安静处理） | 单测 |
| 5 | 老客户端不带 `upload_id` → 行为不变且不写进度表 | 单测 |

| 8 | 进度条有真实填充 + 不确定态 + 30/70 分段 | 前端守卫 |

## 六、仍然没做

- 进度只覆盖「上传 + 建索引」这一段，**大模型生成**仍然只有流式打字（那本身已经是进度）；
- 上传期间不能取消（想取消得引入任务取消语义，代价比收益大）；
- 进度是进程内的：多实例部署时轮询请求必须落到同一个进程（现在单机，暂不涉及）。
