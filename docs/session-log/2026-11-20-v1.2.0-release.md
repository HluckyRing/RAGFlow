# 2026-11-20 发版：v1.2.0（拆问 / 覆盖说明 / 范围词 / 安全闸门）

> 本轮唯一任务：判断「GitHub Releases 停在 v1.1.0 一个多月，现在该不该发新的」，然后发。
> 结论是**该发**，且当轮就发完了。这篇记的是**判据**和**发版链路上踩的坑**，功能细节看
> `docs/release-notes-1.2.0.md`。

## 一、结论怎么来的（发版判据，下次照着抄）

| 判据 | 实测（2026-11-20） |
|---|---|
| 落后多少 | v1.1.0 打于 2026-10-05，`main` 已领先 **79 个提交**（43 个 feat/fix/perf/refactor） |
| 同步 | `main == origin/main == b4da782`，工作区干净 |
| CI | main 上最近一次 push 的 CI **success** |
| 测试 | `.venv\Scripts\python.exe -m pytest tests -q` → **768 passed / 29.78 s** |
| 文档 | `scripts/sync_readme.py --check` 一致（768 条 / 2691 行） |

**为什么不等其余待办**：待办 1–7 全是长线研究/测量/安全（小节级缺口定位、真实流量、用户研究、
更大语料、真身份体系），没有一条有近期终点，而且每条都能无限期当「再等等」的理由；发版不依赖
它们，但要把它们**如实写成「已知限制」**。这条判断比数字更重要：**release 的门槛是「绿色 +
能说清限制」，不是「待办清空」。**

一处提醒：`MEMORY.md` 当时还写着「全部未推送」，而实际早就推到 `b4da782` 了 —— 涉及远端状态
**当场 `git ls-remote` 核对，别沿用上一轮的结论**。

## 二、发版链路（照 AGENTS.md 116 行，一处补充）

1. `pyproject.toml` `version = "1.1.0"` → **`1.2.0`**（新增功能 + 默认值变化 = 次版本）。
2. 新增 `docs/release-notes-1.2.0.md`：亮点（拆问 / 覆盖说明 / 范围词 / 双路融合与拒答链路 /
   安全闸门与 README 自动化）、**破坏性变更**、默认值变化表、**已知限制**、验证。
3. 本地 `python -m build --wheel` → `ragflow-1.2.0-py3-none-any.whl`（37 entries、`index.html`、
   **12 个 vendor 文件**）+ `pytest` 全绿 + `sync_readme.py --check` 一致。
4. 一个提交（`2157668`）→ 推 `main` → `git tag -a v1.2.0 -m "v1.2.0"` → 推标签。
5. `publish.yml` 按 `v*` 触发：18 s 建好 Release，附件 `ragflow-1.2.0-py3-none-any.whl`
   （791 593 字节）。
6. **补充的一步**：`gh release edit v1.2.0 --notes-file docs/release-notes-1.2.0.md`
   把自动正文换成手写正文（见坑 1）。
7. 回读：`gh release list` 里 v1.2.0 = **Latest**；`git ls-remote --tags origin` 有 v1.2.0
   （tag 对象 `1f9a78c` → 提交 `2157668`）；下载附件抽查 37 entries / `index.html` /
   12 vendor 文件 / `METADATA` 的 `Version: 1.2.0`；main 上 CI 2m11s success。

## 三、坑（五条）

1. **`--generate-notes` 对「直推 main、没有 PR」的仓库等于空正文**。v1.1.0 的 release 正文
   只有一行 `**Full Changelog**`，本轮自动生成的也是同一行 —— 79 条提交照样抓不到东西。
   修法：手写 `docs/release-notes-1.2.0.md` 入库，发完用 `gh release edit --notes-file` 补。
   **没动 `publish.yml`**（工作流改动无法在本地验证，收益只有省一条命令），代价是「重跑标签
   会退回空正文」这个已知缺口。
2. **别拿 wheel 字节数比对**。本地 Windows 构建 792 031，CI Linux 构建 791 593（zip 时间戳/
   压缩差异），得抽查**内容**：entries 数、`index.html`、vendor 个数、`METADATA` 里的 Version。
3. **PowerShell 会把 `gh` 的表达式拆成多个参数**。`--jq '.a | "\(.b)"'` / `--template '…'`
   都报 `accepts 1 arg(s), received N`。一条表达式一条命令，或退化成无空格的 `.assets[].name`
   这种路径。
4. **`--generate-notes` 的正文改不了历史 Release 的「Latest」归属**：v1.2.0 建好即自动 Latest，
   不需要手工改（`gh release list` 的 `Latest` 列可核）。
5. **破坏性变更必须写进 notes 才算发完**：本版两条 —— ① 绑定非回环地址且没设 `AUTH_TOKEN`
   时**拒绝启动**（老部署升级会起不来）；② `CHUNK_SIZE` 默认 600 → 480（旧索引要重建才与
   实测口径一致）。这类「升级即炸」的变化，藏在 79 条提交里没人会翻。

## 四、发出去了什么（`v1.1.0..v1.2.0`，79 提交）

检索层：查询分解默认开（复合问 45.9% → 81.1%，多轮省略式 25.0% → 75.0%）、文件内跨节取样
（整章枚举，PPT 97% / ML PDF 93%）+ **覆盖说明**（context 前缀 + SSE `coverage` + 前端标签）、
**范围词当文件过滤器**（事实核 11/14 → 13/14、目标文件 11/12 → 12/12）、双路融合 +
关键词兜底缓存、可答性判断（默认关）、拒答可见 / 不挂 sources / 报「已检索 N 个文件」、
部分可答（过度拒答 5/8 → 0/8）、跨编码器精排（默认关）。
工程侧：公开监听 fail-closed、按 IP 限流 20/60 s、闸门措辞表外置 `src/gates/`、
README 机械部分自动化（`sync_readme.py` + CI `--check` + pytest 守卫）、两条「文档不漂移」守卫。

## 五、还没做的（写进了 notes 的「已知限制」）

覆盖说明只有总账（说不出少的是哪几节）；没有真身份体系（单一共享 `AUTH_TOKEN`，无账号 /
会话归属 / CSRF，限流是进程内内存）；测量只在单一小语料（最大 13 文件 / 1 061 块）+ 12 条
真实提问上做过，**拆问在真实流量里从未被触发**；枚举整章那种提问生成 17.8 s、context 上限
8 000 字符。
