# 2026-11-26 删文件要等 3 分钟：定向删除 + 批量 embedding + 前端即时反馈

> 用户反馈：「不小心上传错文件想删除，发现删除时很慢也没自动刷新，要我手动刷新了。」
> 这不是错觉 —— 是两个真问题叠在一起：后端删一个文件会**重建整份索引**，前端在等的时候
> **一点反馈都没有**。

## 一、实测（在临时对话里量，没碰用户数据）

| 操作 | 改前 | 改后 |
|---|---|---|
| 删 1 个文件（剩 ~17 块） | **4.37 s** | **0.08 s** |
| 删 1 个文件（剩 ~9 块） | 2.27 s | 0.05 s |
| 删整个对话（对比用） | 0.02 s | 0.02 s |
| 上传 250 块（26 万字） | 估 ~62 s（逐块写，按 0.25 s/块推算） | **13.6 s（实测）** |

用户真实语料：4 个对话 / 32 个文件 / 389 473 字 ≈ **811 块**。按改前的口径，删一个文件要
重新 embedding 剩下的全部块，**约 3 分钟**；界面上这段期间什么都不会变。

## 二、根因

**① 删除走了「整份重建」**（`src/server.py`）：

```
_remove_file() → _rebuild_collection()   # 把剩下所有文件重新切片 + 重新 embedding
```

删除根本不需要 embedding —— 只需要把该文件的 chunk 删掉。

**② `_rebuild_collection` 是逐块写**：

```python
for i, (chunk, meta) in enumerate(pairs):
    collection.add(documents=[chunk], ids=[cid], metadatas=[...])   # 每块一次 embedding 调用
```

811 块 = 811 次调用。同一段问题也让「上传多文件」很慢。

**③ 前端点确认后弹窗立刻关、什么都不显示**：`refreshView()` 要等 `DELETE` 返回才跑，
慢的时候用户看到的就是「点了没反应」，于是手动刷新（那时后端其实已经删完了）。

## 三、三条改法

**A. 定向删除**（`_delete_file_chunks`）：`collection.delete(where={"file_name": name})`，毫秒级。
**但不能无脑删** —— P2 之前的老索引 metadatas 里没有 `file_name`，这种 where 过滤会
**静默删 0 条**（不抛错），后果是检索还召回已删文件的内容，**比慢更糟**。所以删完校验两件事：

1. 该文件名的 chunk 一条不剩；
2. `collection.count()` == 「剩下文件重新切片」的块数（切片是纯字符串操作，不花 embedding）。

任一不满足就退回 `_rebuild_collection`（慢但正确）。

**B. 批量 embedding**（`EMBED_BATCH = 64`）：一次 `add` 写 64 块。实测 250 块从「估 62 s」
降到 **13.6 s**；811 块的整份重建同理。

**C. 前端乐观更新 + 处理中态**：
`confirmDialog` 现在 **await onOk 才关弹窗**、按钮禁用并显示「处理中…」（顺带堵住「连点两次触发两次删除」）；
`confirmDeleteFile` 先本地移除该行 + toast「正在从索引里移除…」，服务端返回后以它为准，**失败回滚**。

## 五、教训

- **「删一个东西」不该触发「重建一切」**：这是典型的数据结构选错带来的 O(N) 操作。
  chunk 的 metadatas 里本来就有 `file_name`，定向删除一直是能力内的。
- **快路径必须带一致性校验**：老数据没有元数据时 where 过滤**静默失败**，这类「不报错的错」
  比异常危险得多 —— 所以「删完数一遍」这条不能省。
- **慢请求没有反馈 = 用户眼里的 bug**：前端逻辑其实是对的（会刷新），但「等 3 分钟且毫无动静」
  和「坏了」在体验上没有区别。
- 批量写这种改动收益与语料规模线性相关：小样本（3 个文件）几乎看不出差别，真实语料才显形 ——
  所以**测量要用真实规模的语料**。

## 六、仍然没做

- 上传本身还没有进度条（250 块要 13 s，用户会等）；
- 删除只清了索引与原件，对话里**已生成的回答**仍保留（这是有意的：历史消息不该被追溯删除，
  但用户可能期望「引用了该文件的回答也标灰」）；
- 重建仍是「全量重写」：如果将来要支持「只重算一个文件」，得把 chunk id 做成可定位的
  （`file_name + 块号`），那是另一件事。
