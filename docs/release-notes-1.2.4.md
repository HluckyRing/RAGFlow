# v1.2.4 — 上传进度条

> 一次请求的体验改进：上传不再是「一句『仍在解析中…』然后干等」。**没有破坏性变更**，
> 也不用改配置。回退：退到 v1.2.3。

## 亮点

### 上传现在有真实进度

上传的时间几乎全花在**服务端**（解析文件 → 切片 → 逐批 embedding，实测 26 万字 / 160 块要
13–27 秒），所以进度由**后端上报真实阶段**，不是前端按时间猜：

| 阶段 | 界面显示 | 进度 |
|---|---|---|
| 解析 | `解析文件 2/3：第2章.pdf` | 前 30% |
| 建索引 | `建立索引 128/160 块（12.4s）` | 后 70%（每 64 块跳一次） |
| 完成 | 100% 后 600 ms 淡出 | — |

拿不到总量（还在切片）时显示**不确定态**的滑动条，绝不假装一个百分比。

实测（真实容器，160 块）：轮询 99 帧，`parse 1/1` → `index 0/64/128/160` → 100%。

### 实现上没有引入任务队列

- 上传接口保持同步（「返回即落盘」这个语义不变）；
- 前端生成 `upload_id` 随 multipart 发过去，后端在内存表里记阶段，**上传结束（含失败）
  就删条目**，并带 300 s TTL 顺手回收；
- 前端 400 ms 轮询 `GET /api/upload/progress`（带 `session_id`，走同一套归属校验 ——
  别人的上传任务查不到，403）。

### 修掉一个真竞态

第一版前端「遇到 404 就停止轮询」，实测**轮询帧数 0**：第一次轮询常常比后端建进度条目更早
（POST 还在路上），一帧都没拿到就停了，界面永远停在「准备中…」。现在错误分支不终止轮询，
只由调用方（上传成功/失败）收起。

## 升级注意

1. `git pull && python scripts/update_deploy.py`（Docker 用户会重建镜像）；
2. **浏览器 Ctrl+F5 硬刷新**（前端有改动）；
3. 不需要改任何配置。

## 已知限制

- 上传期间**不能取消**（要引入任务取消语义，代价大于收益）；
- 进度是进程内的：多实例部署时轮询必须落到同一进程（当前单机部署，不涉及）；
- 进度只覆盖「上传 + 建索引」；大模型生成本来就是流式打字，不需要额外进度。
